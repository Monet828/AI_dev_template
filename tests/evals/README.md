# Skill Evals

各 skill が「読まれたときに、実際に挙動を変えるか」を確かめるための評価シナリオ。

公式ガイダンスは **「詳細なドキュメントを書く前に eval を書け」** と明言している。
理由は、eval を書こうとすると **その skill が生む観測可能な差** を名指しせざるを
えなくなるからである。名指しできないなら、その skill はまだ何も約束していない。

## ここは生成物に含まれない

`tests/evals/` はリポジトリ直下に置き、`template/` には入れない。
skill を**書く側**の道具であって、生成されたプロジェクトで**使う側**には要らない。
`scripts/setup/scaffold.sh` は `template/` しか複製しないため、生成物へは漏れない
（`tests/regression/cases/40_skill_contract.sh` がこれを検査する）。

## 最も重要な規律

> **skill を読まなくても通る eval は、何も測っていない。**

だから各 eval は「期待する挙動」だけでなく **「落ちる挙動」** を必ず書く。
落ちる挙動は、**skill が無ければ有能なエージェントでも普通にやってしまう、
もっともらしい間違い**でなければならない。
「明らかに馬鹿げた挙動」を落ちる挙動に置いた eval は、常に通る。それは飾りである。

## ファイル形式

`tests/evals/<skill-name>/NN-<slug>.md`。skill 1件につき **3件以上**。

必須見出しは4つ。欠けていると `40_skill_contract.sh` が落ちる。

```markdown
# NN-<slug> — <一行で何を測るか>

## シナリオ
エージェントに与える入力と状況。

## 期待する挙動
**観測可能な**合否条件。「〜を理解する」は不可。
「〜を出力する」「〜をしない」「〜を先に読む」のように、外から見える形で書く。

## 落ちる挙動
skill が無い、または無視された場合に出る、もっともらしい間違い。

## 判定
`human`（人間が読んで判定）または `mechanical`（スクリプトで判定可能）。
```

## 実行

**機械的な検査**（CI で毎回走る）:

```bash
./tests/regression/run.sh   # 40_skill_contract.sh が構造・仕様適合を検査する
```

**挙動の評価**（オンデマンド。LLM が要るので CI では走らせない）:
skill を読ませた状態で「シナリオ」を入力し、「期待する挙動」と「落ちる挙動」の
どちらに寄ったかを人間が判定する。判定結果は `memory/evidence-log.md` に、
**日付と、どのモデル・どのバージョンの skill で測ったか**を添えて残す。

> [!important] 機械的検査は挙動を保証しない
> `40_skill_contract.sh` が緑でも、それは **eval が存在し形式が整っている**
> ことしか意味しない。**skill が効いていることの証明ではない。**
> この2つを混同しないこと（`AGENTS.md` §3）。
