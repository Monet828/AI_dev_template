# spec-first

この pack は、**承認済みの仕様が無いうちに製品コードを書かない**ための資産であり、
scaffold 時に本体テンプレへマージされる。既定で全プロファイルに入る。

規則の正本は `spec.md`（この pack 内）。生成プロジェクトへは配らない。

## 何を解決するか

守りたいものが2つあり、**解き方が違う**。片方を満たしてももう片方は満たされない。

| | 何を守るか | 手段 |
|---|---|---|
| **A 理解の担保** | ユーザーが理解していないものを土台にしない | 対話と状態マーカー（`authoring-specs` Skill） |
| **B 逸脱の防止** | 承認していないものを実装に混ぜない | 承認記録と適合検査 |

具体的には、こういう失敗を止める。

- 曖昧な返事（「いいね」「よさそう」）や無返答を承認として扱う
- 要件の承認を、技術構成の承認と読み替える
- 実測が仕様と食い違ったとき、黙って実装で回避する
- 決めたはずのことが会話に流れて、次のセッションで消えている

同時に、**止めすぎない**ことも仕様に書いてある。既存プロジェクトへの後付けでは
導入時点の実装を現状追認し、今回の範囲に影響しない未確定事項は
ブロッカーとして扱わない。手続きが重すぎて使われなくなるのが最大の失敗である。

## 基本思想

1. 実装前に、承認済み仕様があるかを確認し、**1行で見せる**（黙って進めない）
2. 質問は一度に3問まで。往復5回を超えたら整理を出して選ばせる
3. 要件・設計・実装計画を**分けたまま**承認する
4. 承認はコミットハッシュとともに `docs/approvals/` に記録する
5. 仕様に従えない状況（誤り／変更／不足）は**異常ではなく通常の経路**として扱う

## パック構造

- `spec.md`
  - 規則の正本。この pack が何を要求するかの全文
- `pack-manifest.sh`
  - pack の基本情報と merge 元ディレクトリを定義する
- `merge/`
  - 新規プロジェクトへそのまま配置されるファイル。
    **雛形は `docs/templates/spec.md` の1つだけ**（運用ルールもその末尾にある）
- `append/`
  - 既存ファイル末尾へ追記される断片（`AGENTS.md`）

対話の手順は Skill 側にある（`template/skills/authoring-specs/`）。
`AGENTS.md` へ足すのは判断の入口だけに留めている。
毎セッション読まれる場所を膨らませないため。

## 導入

新規プロジェクトには直接コピーせず、base template の scaffold から適用する。
既定で入るので、外したい場合だけ `--packs` で明示的に除く。

## 使い方

1. `./scripts/workflows/spec-first.sh new-spec <name>` で雛形を出す
2. 対話して埋める。**全行に `[確定]` / `[候補]` / `[未定]` を付ける**
   （AIが書いた行は必ず `[候補]` から始まる）
3. 応答のたびに「空欄／候補のまま／未定で進行中」の3行が出る。
   **気を利かせて指摘するのではなく、機械的に列挙する**
4. コミットしてから承認を求める。ハッシュの無い承認記録は照合できない
5. `docs/approvals/<name>.md` に承認を記録する（`_TEMPLATE.md` を使う）
6. `./scripts/workflows/spec-first.sh status` で仕様と承認の対応を見る
7. 実装とテストに要件IDを記す。`unlinked` が持たない変更ファイルを列挙する

`status` は承認後に仕様が変わっていれば警告する。

```
承認済み (6deb0e2) 仕様は承認時から変わっていない
⚠ 承認後に仕様が変わっている (6deb0e2) → 実装を止めて再承認を求める
```

## 限界

要件IDは書けば通る。**防げるのは書き忘れであって、偽装ではない。**
`unlinked` の列挙は「未達」ではなく「要確認」であり、
設定ファイルや自動生成物など紐づかないのが正しいものも含む。
