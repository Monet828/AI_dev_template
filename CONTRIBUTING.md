# Contributing to AI_dev_template

This is a small, personal template harness. Contributions are welcome, but keep
changes proportional to the project's size -- see the non-goals in
[README.md](README.md).

## Repository layout (read this before editing)

This repo has two distinct roots that are easy to mix up:

- `template/` -- everything that gets copied into a generated project.
  Edit here for anything an end user of the template should see (`AGENTS.md`,
  `CLAUDE.md`, `scripts/hooks/`, `scripts/loop/`, `scripts/setup/{bootstrap,
  doctor,lib}`, `memory/` templates, `docs/`, `app/`, `src/`,
  `skills/`, `assets/`).
- Repository root -- the generator itself. `scripts/setup/scaffold.sh` and
  `scripts/setup/new-project.sh` build a project from `template/` plus
  `packs/`; neither of those two scripts, nor `packs/`, nor `tests/` is ever
  copied into a generated project.

If you're not sure which root a change belongs in, ask: "would a person using
a project generated by this template ever see this file?" If yes, it belongs
under `template/`.

## Making a change

1. Fork/branch from `main`.
2. Make the smallest change that accomplishes the goal. Prefer editing an
   existing pack or template file over adding new abstraction.
3. Add or update a test in `tests/regression/cases/` if you changed
   `scaffold.sh`, `new-project.sh`, `doctor.sh`, or `verify.sh` behavior.
   See `tests/regression/README.md`-equivalent conventions: each case file
   sources `tests/regression/lib/assert.sh`, uses a `mktemp -d` + `trap`
   for cleanup, and exits 0/1 via `assert_case_result`.
4. Run the full local check before opening a PR:
   ```bash
   find . -type f -name '*.sh' -not -path './.git/*' -print0 | xargs -0 -n 1 bash -n
   shellcheck $(find . -type f -name '*.sh' -not -path './.git/*')
   ./tests/regression/run.sh
   ```
5. Open a PR against `main` describing what changed and why.

## Adding or changing a skill

Skills live at `template/skills/<name>/SKILL.md` and are loaded on demand, so
only `name` and `description` sit in context by default. That makes the
frontmatter the load-bearing part: if the description doesn't say *when* to
reach for the skill, the skill is never read.

**Write the evals before the SKILL.md body.** Evals live at
`tests/evals/<name>/` (repo root -- they are a skill *author's* tool and never
ship into a generated project) and there must be at least 3 per skill. Writing
them first forces you to name the observable difference the skill is supposed
to make; if you can't name one, the skill isn't ready to be written. See
`tests/evals/README.md` for the file format and the one rule that matters:
**an eval that passes without the skill loaded measures nothing.**

`tests/regression/cases/40_skill_contract.sh` enforces the mechanical half of
this -- frontmatter shape, `name` matching the directory, description size,
SKILL.md under 500 lines, at least 3 well-formed evals, no orphan eval
directory, and that every `` `AGENTS.md` §N `` reference resolves to a real
section. It cannot check whether the skill actually changes behavior; that is
judged by hand against the evals.

If you renumber a section in `template/AGENTS.md`, run
`./tests/regression/run.sh` -- the stale `§N` references in skills are exactly
what case 40 exists to catch.

## Adding or changing a pack

- A pack lives at `packs/<name>/` with a `pack-manifest.sh` (`PACK_NAME`,
  `PACK_VERSION`, `PACK_DESCRIPTION`, `PACK_MERGE_DIR`, `PACK_APPEND_DIR`),
  a `merge/` tree (files copied as-is into the generated project, same
  relative paths), and an `append/` tree (fragments appended to files that
  must already exist in the generated project -- typically `AGENTS.md`).
- Bump `PACK_VERSION` when you change a pack's `merge/`/`append/` content;
  it's recorded verbatim into every generated project's
  `.ai-dev-template.yml`.
- `pack-manifest.sh` is `source`d by `scaffold.sh`, not executed as a
  subprocess -- keep it to plain variable assignments. See `SECURITY.md`
  for why this matters.

## Bumping the template version

`VERSION` at the repository root is the single place `template_version` is
read from. Bump it when you make a change that meaningfully affects what
gets generated.
