# 仕様策定

このSkillは仕様書駆動開発の **A系（理解の担保）** の実体である。
規則の正本は AI_dev_template の `packs/spec-first/spec.md`。

**目的は2つあり、解き方が違う。**

| | 何を守るか | 手段 |
|---|---|---|
| **A 理解の担保** | ユーザーが理解していないものを土台にしない | このSkill（対話） |
| **B 逸脱の防止** | 承認していないものを実装に混ぜない | 承認記録と検証 |

片方を満たしてももう片方は満たされない。

---

## 1. 入口 — 実装を始める前に

**承認済み仕様が無ければ、製品コードを書かない。**
読み取り調査・仕様整理・既存コードの確認は進めてよい。

段階を判定して、ユーザーに1行で見せる（REQ-B01）。

```
仕様: docs/specs/<name>/requirements.md v0.2.0 ／ 承認: 要件のみ ／ 段階: 設計確認待ち
```

内部で確認して黙って進めない。**見せる。**

---

## 2. 構想を受け取る

長いフォームへの記入を求めない（REQ-A01）。文章、箇条書き、参考資料、
断片的なアイデア、既存コード、どれからでも始める。

**最初にやることは質問ではなく整理。** 受け取ったものを自分の言葉で
組み直して提示し、そこから聞く。

### 発言と判断を混ぜない（REQ-A02）

| 区別するもの | 書き方 |
|---|---|
| ユーザーの発言 | そのまま引用する |
| AIの解釈 | 「〜と理解した」と明示 |
| AIの提案 | 「〜を提案する」と明示 |
| 未承認の候補 | **候補として記録する。要件に昇格させない** |
| 承認された内容 | 承認記録にハッシュ付きで残す |

「こういうものもよさそう」を実装要件として確定しない。

出典の追跡は、ユーザーが提示した資料（ファイル・URL・コード）に対してのみ。
会話ログへの逆参照は求めない。追跡できないなら「ユーザー発言に由来」とだけ書く。

---

## 3. 質問する（REQ-A03）

- **一度に3問まで。**
- 回答済みを繰り返し聞かない。
- 推奨案には理由と代替案を添える。**未回答を承認として扱わない。**
- 影響の大きい曖昧さ・矛盾から聞く。細部を先に聞かない。

### 打ち切り

**往復が5回を超えたら**、現状の整理を提示して選ばせる。

> このまま詰めますか、範囲を絞って着手しますか。

範囲を絞る場合、ブロッカー判定は**絞った範囲に対して**行う。

### 未確定がゼロになるまで待たない

今回の実装範囲に影響しない未確定事項は、**ブロッカーではないものとして記録し、
着手してよい**。どれがどの作業を妨げるかは仕様に書く。

### 規模の目安

| | 目安 |
|---|---|
| 1仕様の要件数 | 7〜10 |
| 1要件の受入条件 | 3〜7 |
| 実装タスク | 10〜14 |

**要件が15を超えるなら仕様を分割する。**

---

## 4. 様式を選ぶ

**AIが提案し、ユーザーが選ぶ。**

| | いつ | ファイル |
|---|---|---|
| **lite** | 小規模な追加・変更、単発のツール、検証用の試作 | `docs/templates/spec-lite.md` |
| **full** | 独立した機能単位、複数画面、他者が引き継ぐ可能性 | `docs/templates/spec-full/` |

`./scripts/workflows/spec-first.sh new-spec <name> [lite|full]` で雛形が出る。

### 要件の書き方（REQ-A05 / 5.3）

```
〔契機・条件〕のとき、システムは〔動作〕する
〔条件〕のとき、システムは〔動作〕してはならない   ← 禁止動作
```

**整形はAIが行う。ユーザーに記法を守らせない。**
記法を埋めることより、曖昧さを減らし検証できることを優先する。

### 要件と設計を分けたまま承認する

- **要件** … 目的、利用者、範囲、期待する動作、制約、成功条件
- **設計** … 画面、データ、処理の流れ、技術構成、外部依存、責務分担
- **実装計画** … 作業順序と検証方法

**要件を確認しただけで、未確認の技術構成による実装を始めない。**

---

## 5. 承認を得る（REQ-B02）

対象ファイル・対象範囲・版を明示して求める。

| 承認とする | 承認としない |
|---|---|
| 「承認する」「これで進めて」「OK、実装して」 | 「いいね」「なるほど」「よさそう」／**無返答** |

曖昧な返答なら、対象を明示して**再確認する**。

記録は `docs/approvals/<name>.md`（`_TEMPLATE.md` を使う）。
**未コミットなら、コミットを促してから承認を求める。**
ハッシュの無い承認記録は照合できない。

**AIが承認状態を自作して実装を開始してはならない。**
要件の承認を設計の承認と読み替えない。
承認済みの同じ範囲について繰り返し承認を求めない。

---

## 6. 逆向きの経路（REQ-B07）

**仕様に従えない状況は異常ではない。通常の経路として扱う。**

| 種別 | 何が起きたか | 気づくのは |
|---|---|---|
| **誤り** | 仕様の記述が事実と異なる | AI（実測で判明） |
| **変更** | 事情が変わり、要件が変わった | ユーザー |
| **不足** | 実装して初めて、決めていない論点が出た | AI |

1. 該当範囲の実装を止める。**黙って実装で回避しない。**
2. 種別・該当箇所・根拠（実測値／出典／発言）を提示する。
3. ユーザーが選ぶ：**仕様を直す／実装を仕様に合わせる／保留して記録**。
4. 「仕様を直す」なら正本を更新し、承認記録を新しい版で作り直す。

**AIが仕様を勝手に直さない。同時に、誤りと分かって黙って実装しない。**

**変更を例外扱いしない。** 実装中に要件が変わるのは通常のこと。
特定の要件の範囲に収まるなら、その要件だけ再承認すればよい。
仕様全体の再承認を求めない。

記録先: full は `changes.md`、lite は仕様末尾の変更履歴節。

---

## 7. 実装に入るとき

実装とテストに**要件IDを記す**（REQ-B08）。

```python
def resolve(ref: str) -> Path:
    """素材参照を解決する（REQ-004）。"""
```

適合検査が、要件IDを持たない変更ファイルを列挙する。
**列挙は「未達」ではなく「要確認」。** 設定ファイルや自動生成物など、
紐づかないのが正しいものもある。

**限界を隠さない。** IDは書けば通るので、防げるのは書き忘れであって偽装ではない。

---

## 8. 既存プロジェクトへの後付け

既存実装を全部未承認扱いにすると、必須確認が常に停止する。

1. 導入時点で動いている機能・技術構成は **現状追認**。個別の承認記録を求めない。
2. 既存の技術スタック・構造・制約を1文書に書き出し、ユーザーが承認する。
   以後これが既存部分の基準。
3. **既存部分に変更を加える時点で、その範囲だけを仕様化する。**

---

## 9. 状態を落とさない

`memory/current-state.md` に最小限を残す。長い会話でこの仕組みが最初に壊れるのは
ここである。

**書く**: 承認を得た直後 ／ 段階が変わった直後 ／ セッションを終える直前
**読む**: セッション開始時と再開時 ／ 実装着手の直前

保持: 現在の段階・対象仕様のパスと版・承認済み範囲・ブロッカー・次の行動。
**仕様本文を複製しない。** 正本は `docs/specs/`。

---

## 停止条件

- 承認済み仕様が無いのに製品コードを求められた
- 要件の承認しかないのに技術構成の実装を求められた
- ブロッカーの未確定事項が残っている
- 承認記録のハッシュと現在の仕様が食い違う
- **承認済み仕様と実測が矛盾した**（→ §6）
- 委任範囲外の判断が必要になった
